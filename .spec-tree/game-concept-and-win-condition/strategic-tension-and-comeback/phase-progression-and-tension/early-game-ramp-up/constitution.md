# Constitution — Early Game Ramp Up

- Node slug: `early-game-ramp-up`
- Depth: 4
- Parent: `/workspaces/mobile-strategy-game-godot/.spec-tree/game-concept-and-win-condition/strategic-tension-and-comeback/phase-progression-and-tension/`
- Purpose: Define the opening phase with limited objectives, clear learning, readable positioning, and low cognitive load on portrait mobile.
- Claim reference: DEC-GCWC-001 fixed-length visible Claim win condition for Banner of the Majlis.
- Scope: Spec Kit planning artifact only; no Godot game implementation is created here.

## Charter
1. This node protects onboarding-through-play, first Claim clarity, and safe strategic scouting..
2. The match must remain tense from first banner contact through final reveal.
3. Comebacks must be earned through strategic choices, contested objectives, timing, and visible risk.
4. Random handouts, hidden rubber-banding, and unexplained leader punishment are forbidden.
5. The leader keeps meaningful agency and should feel pressured, not cheated.
6. The system must serve 4-player FFA and 2v2 team modes.
7. Portrait mobile readability on a 6-inch screen is mandatory.
8. Android and iOS touch targets must remain comfortable under thumb reach.
9. Arabic and English localization are required; player-facing copy uses keys only.
10. Godot 4.x planning references include Control, Label, TextureRect, ProgressBar, Timer, Signal, AnimationPlayer, and Resource.
11. Presentation must feel like a strategic game board, not a spreadsheet.
12. This node may define tasks but must not implement scenes or scripts now.
13. Balance numbers are provisional and require future simulator validation.
14. Any bonus must have an eligibility rule, cap, UI explanation, and abuse test.
15. Any phase shift must be predictable enough for planning but dynamic enough for tension.
16. Any leader pressure must arise from public Claim state, not hidden AI intervention.
17. Every child branch must reach depth 4 and remain meaningful.
18. Dependencies must be passed to future core-match-systems and balance-and-validation nodes.
19. QA must ask whether trailing players see a believable path back.
20. Reviewer must reject outcomes where the first leader is usually uncatchable.
21. Integration must avoid controlling rendering from rules logic directly.
22. Signals should describe state changes, such as tension_changed or comeback_window_opened.
23. State ownership belongs to future Game Rules; UI only observes.
24. This artifact is complete only with checklist, tasks, analysis, and NODE_SUMMARY alignment.
